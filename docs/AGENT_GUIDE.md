# 让自己的 Agent 协助完成部署

客户日常操作优先使用浏览器工作台，不要求安装 Azure CLI 或编辑 JSON。部署者启动 Docker 或执行 `python -X utf8 foundry_models.py web`；客户本人完成 Microsoft 登录和 MFA，再在网页选择订阅、模型、区域及命名。创建前须确认具体检查清单。下面命令仅用于客户明确要求 Agent 自动化的场景，统一调用 `foundry_models.py`，不要额外维护另一套创建逻辑。

可以把本公共仓库的链接或解压目录交给客户自己的 Agent。不要把应用 Secret、账户 Key、管理员密码或验证码发进 Agent 聊天。Agent 需要访问 Azure 时，应在客户控制的电脑、Cloud Shell 或受控运行环境里执行脚本。

## 可直接复制给 Agent 的任务

> 请使用本仓库帮助我在自己的 Azure 公有云租户批量部署生图和文本模型。先阅读 README、AGENTS.md 和两份操作文档，用中文沟通。客户优先通过网页操作；若我要求命令自动化，再使用统一入口并检查依赖及登录环境。只问缺失的租户、身份方式、试点订阅、模型/SKU、批准区域及命名规则。网页默认 Azure 默认版本与最大合法 TPM/RPM；脚本需填写目录返回的精确版本。先只读扫描，列出需创建、已有和失败项。不要索要或上传密码、验证码、Secret、Key、真实配置及结果。取得我对具体清单的确认后才创建/授权，先做一个订阅试点。执行后核验 ARM 实际状态、Project 和模板 Excel，分别汇报成功与未完成项；超时先重扫，不盲目重放写入。不调用付费推理。

## 应该反问客户什么

把问题分成三轮，只问尚未给出的内容，避免一次让客户填几十项。

### 第一轮：环境与身份

1. 客户 Azure **资源租户 ID** 是什么？是否为 Azure 公有云？不要仅根据邮箱域名推断租户。
2. 用已有管理员登录直接部署，还是用应用身份？已有应用时，只询问客户端 ID 和私密凭据**本地路径**，不要询问密钥值。
3. 从哪个明确的测试订阅开始？完整范围是本租户所有可见订阅还是指定 ID 列表？

若使用管理员身份，让客户在同一运行环境完成 `az login --tenant ...`，MFA 由客户完成。网页登录、另一个操作系统或容器中的登录缓存不能代替该步骤。应用身份由 SDK 获取令牌，无需另做 `az login --service-principal`。

### 第二轮：部署配置

1. 选择哪些生图或文本模型？支持列表见 README，也可在网页多选。网页默认使用 Azure 默认版本；脚本需要目录返回的精确版本。部署类型是否使用默认 GlobalStandard？不凭别名猜测版本。
2. 批准哪些区域及数据处理范围？`GlobalStandard` 并不表示推理只在资源所在区域处理，不能用创建区域代替数据驻留要求。
3. 默认使用 `auto`：读取实际余额并在执行每项前重新检查，不要求客户先判断配额共享范围，也不保证全部区域同时达到目标。若客户提供了明确的共享池信息，可选择对应高级模式；客户只要检查而不安排创建时选择 `unknown`。
4. 客户确认的资源组、账户、部署命名是什么？现有多个账户时，用明确命名选取目标，不随机复用。
5. 新建账户使用 Azure 默认网络设置是否符合客户要求？若需要私有端点/指定防火墙，此版不自动配置，先交由客户完成网络设计，不直接用默认设置执行。
6. 应用初始化是否需要新应用或新增密钥？密钥有效期、角色范围、私密文件路径是什么？已有应用默认不新增密钥。

### 第三轮：具体写入确认

先给客户一页摘要：试点订阅、模型/版本/SKU、每个区域的账户与部署名、将创建/复用/跳过的数量、容量、预计 RPM、共享池剩余、所有阻塞与读取失败，以及需要新增的 Contributor 授权、应用密钥、账户网络设置。然后询问：

> 已生成上述明确清单。是否现在按此清单执行这个试点订阅的创建/授权？是否读取账户 Key 并仅保存至指定本地私密文件？其他失败项将保留，旧部署和旧密钥不改动。

客户如果已明确批准相同清单、身份、范围和动作，不重复索要确认。范围、命名、容量或所用身份改变时重新展示差异；旧清单不能直接继续执行。

## Agent 的执行顺序

1. 读取文件与 Git 状态，创建本地虚拟环境，安装锁定的直接依赖；不改系统 Azure 登录设置来掩盖身份错误。
2. 执行 `self_test.py` 和 `doctor --offline`，确认没有环境问题。应用方式用 `--auth app`，不要因没有 CLI 而阻止它。
3. 填写 `config.json`，保留 `.gitignore`。运行只读 `doctor`，只输出通过/未通过及可见订阅数量，不展示 Token。
4. 如需初始化应用，先运行无 `--execute` 的 `setup-app`。角色检查失败时不得声称已有授权；确认后才写入。
5. 运行 `scan`，读取所有 `rows` / `errors`。失败列表不是空白成功列表；某个订阅无法枚举全部账户部署时，不创建以免重复。
6. 确认试点清单后执行一次 `deploy --execute`，普通报告、应用凭据、账户 Key 使用不同文件路径。输出路径要事先能写入且不存在，不能覆盖旧密钥。
7. 对成功项检查真实资源状态及实际 `capacity` / `rpm` / Endpoint；对失败项按文档分类。不为了把结果变成全绿自动换区域或更换模型。
8. 客户验收试点后，再将订阅范围扩展并重新扫描确认。记录实际成功、已有、阻塞、失败；不能只根据退出码或 Python 自检宣称全部可用。

## 什么时候必须停下

- 模型版本无法确认、实际配额无法读取、租户/身份不一致、没有具体写入授权。
- 订阅枚举失败、未知模型版本、同名应用不唯一、区域多个可复用账户而目标不明确。
- 登录要求 MFA/条件访问/管理员同意；交给客户处理，不索要认证信息。
- Azure Policy、锁或 Key 禁用阻止执行；不解除限制或自动提升权限。
- 写入超时或账户处于 Creating/Failed；先核对 Azure 实际状态，不创建第二份。
- 客户要求跨云、自动建立私有网络、跨机器并发写入、覆盖已有部署或更换密钥；这些不属于本脚本默认流程，先明确新范围。

## 客户验收摘要模板

| 项目 | 需要记录 |
| --- | --- |
| 操作范围 | 客户确认的租户/订阅范围；对外转发时脱敏 |
| 配置 | 模型、版本、SKU、区域、配额范围、命名 |
| 创建情况 | 成功、已有、阻塞、失败与未尝试数量 |
| 实际结果 | 部署状态、capacity/RPM、Endpoint 本地结果路径 |
| 私密信息 | 凭据/Key 的保存位置与访问要求；不填写值 |
| 未完成项 | 权限、网络、配额、异常/中断及下一步 |
| 真实验收 | 哪些已在 Portal 核对，哪些尚未实际调用验证 |
